# 作者工作台（本地写作台）

作者工作台是一个只在您自己 Mac 上运行的网页式写作工具（studio v0.1.1）。打开后默认
进入**文章管理首页**：浏览、搜索、新建、编辑 `content/` 里的所有文章，也可以
随时切换到 Word 导入向导，按六个步骤把 Word 稿件导入为网站草稿。顶栏的
**版本**、**媒体**、**发布**、**反馈**四个页面分别提供 Git 版本管理、
图片媒体库、发布中心与阅读反馈（段评/章评审核）。网站本身仍是 Hugo 静态站，正式访问时没有 Python、数据库或 CMS
常驻进程；工作台只监听 `127.0.0.1`（本机回环地址），同一 Wi-Fi 下的其他
设备无法访问它，文件也不会上传到任何网络位置（只有您在发布中心显式确认
发布时，才会走原有的 `publish` 流程上传服务器）。

## 本轮具备的功能

- 文章管理首页：按栏目/文集分组列出全部文章，显示标题、副标题、状态
  （草稿/已发布）、字数、发布与修改日期、缺少段评锚点提示；草稿排在每组最前；
- Markdown 编辑器：左右分栏（源码 + 近似预览，标注“转换预览，不代表最终网站
  效果”）、可折叠 Front Matter 表单、事务保存（自动备份、原子写入）；
- 新建文章：标题自动建议拼音 slug，作品栏目可选既有文集或新建文集，
  新文章一律是草稿；
- 搜索：标题、副标题、分类、标签、人物、地点、文集与正文的大小写不敏感
  子串搜索，正文命中显示上下文摘要；
- 版本管理：仓库状态（分支、未提交文件清单）、建议提交信息、勾选文件后
  手动确认提交、最近提交列表；每篇文章有独立的版本历史时间线，可展开
  查看任意提交的 diff 或当前未提交修改；
- 媒体库：按文章分组浏览全部插图（尺寸、大小、Markdown 引用一键复制），
  上传自动校正方向/缩放/留原图，删除移入回收站；
- 发布中心：本地版本与发布记录一览、服务器配置状态（只显示“已配置/
  未配置”，永不显示密钥值）、发布前检查（标准/完整）、二次确认后正式
  发布并显示完整日志；
- 阅读反馈：一键启动本机评论服务、站主登录、段评/章评审核（通过/拒绝/
  垃圾/隐藏/删除）、摘录对比、原文定位、“下一条待审核”快捷处理；
- 作者批注：在编辑页右侧预览中，直接点击正文段落旁的“写作者评”；整篇文章
  的作者评及已有批注管理仍在“作者评”面板。批注关联稳定 articleId，并存入
  `data/author-notes/<articleId>.yaml`；发布的批注
  会以前台折叠块显示，草稿和源 YAML 不进入构建产物；
- 预览：一键启动 Hugo 真实预览（含草稿，地址 `http://127.0.0.1:1313/`），
  每篇文章可直接“预览”（自动启动预览并打开对应页面）、“打开目录”；
- Word 导入：导入报告、元数据表单、三个预览标签页、警告点击定位、
  确认后以草稿写入 `content/`；
- 深浅双色（跟随系统，可手动切换并记忆）。

## 本轮不具备的功能

- 不做 Word 与 Markdown 的双向同步（原因见下文）；
- 版本管理只做本地提交，**不提供**推送、回滚、分支切换、贮藏等操作
  （需要时请用终端或 Git 客户端）；也不会定时自动提交；
- 不支持脚注转换（脚注会在导入报告中明确警告）；
- 不支持文集封面（cover）上传与裁剪，封面仍手工放入 bundle 目录；
- 不修改 slug 与 articleId（它们关系网址与段评身份，如需变更请手工处理）；
- 不提供作者对读者评论的公开回复（评论服务没有回复概念；想回应请用
  作者批注或修订正文）；
- 作者批注只有草稿/发布两种状态，不做版本历史（历史靠 git 与保存备份）；
- 多人同时使用、手机远程访问（它只服务本机这一位作者）。

## 本机安全边界

Studio 只绑定 `127.0.0.1`。每个请求在进入路由前还会把 Host 拆分为主机名和
端口，只接受当前监听端口上的 `127.0.0.1`、`localhost` 与 `[::1]`；相似域名、
缺失、重复或畸形 Host 均返回 403。首次打开同源首页会取得 HttpOnly、
SameSite=Strict 的随机会话 Cookie，所有 API 都必须携带它。会话只存在进程
内存中，不写入 URL、日志、Git 或配置，Studio 重启后自动失效。原有 Origin、
`X-Studio-Request`、JSON 写请求和路径白名单仍继续生效。

## 文章管理

启动工作台后默认就是文章管理首页（`#/`）。顶部依次是搜索框、［新建文章］、
［Word 导入］、［启动预览］。文章按“文集 / 随笔 / 资料”分组，每组内草稿排
在最前并有明显的“草稿”徽章。每篇文章一行卡片，操作有三个：

- **编辑**：进入 Markdown 编辑器；
- **预览**：若 Hugo 预览未运行会先自动启动（等端口就绪），然后打开该文章的
  真实页面；
- **打开目录**：在访达中打开该文章的 bundle 目录。

## 编辑与保存

编辑器左侧是 Markdown 源码（衬线大字号、宽文本区，Tab 键不会跳出输入框），
右侧是近似预览（输入停止半秒后自动刷新）。顶部有保存按钮与保存状态；Front
Matter 默认折叠，可编辑的字段有：标题、副标题、摘要、发布日期、weight、
草稿、精选、文集、分类、标签、系列、时代、人物、地点。slug、articleId、
articleRevision 只读展示，不可修改。

保存是**事务**：

1. 读取磁盘现状，白名单之外的字段（slug、articleId、comments、aliases 等）
   一律以磁盘为准，即使前端传了也忽略；
2. `lastmod` 自动更新为当天；
3. 自动为新段落补充段评锚点并更新 articleRevision（原因见下节）；
4. 校验合并后的 Front Matter 可以正常序列化、正文非空；
5. 写入前把当前磁盘文件备份到 `.cache/studio/backups/<栏目>-<slug>/`，
   每篇文章保留最近 10 份；
6. 先写同目录临时文件，再原子替换正式文件；任何一步失败，磁盘上的原文件
   都保持不动。

有未保存修改时离开编辑页，页面顶部会出现拦截条，由您选择“继续编辑”还是
“放弃修改并离开”；直接关闭浏览器标签页也会有系统提示。

### 为什么保存时会自动补段评锚点

网站的段评系统靠正文里 `<!-- paragraph-id:p-xxxxxxxxxxxx -->` 这样的注释
锚点把评论挂到具体段落。正式构建前的只读检查（`scripts/comments-prepare.py`）
规定：有可评论的自然段缺少锚点、或锚点/articleRevision 需要更新，构建就失败。
因此工作台在每次保存时自动执行与 `comments-prepare --write` 完全一致的补锚
逻辑——**已有锚点逐字节保留**（段评不会丢），只有新写的段落会获得新锚点。
这样您只管写正文，锚点永远由工具维护。

### 备份在哪里、如何恢复

每次保存前，旧版本会复制到 `.cache/studio/backups/<栏目>-<slug>/` 下，文件名
形如 `20260731153000-index.md`，每篇文章保留最近 10 份。`.cache/` 不会进入
Git 或发布包。恢复方法：在备份目录找到想要的时间点，把它的内容复制回
`content/` 下对应文章的 `index.md` 即可（恢复后建议再保存一次，让
articleRevision 与正文重新对齐）。

## 草稿与新建文章

本站没有单独的草稿目录，**草稿就是目标栏目内 `draft: true` 的文章**——它
参与本地预览（`--buildDrafts`），但不会进入正式发布构建。新建文章（`#/new`）
填写标题、副标题（可空）、栏目、slug（按标题拼音自动建议，可修改）；栏目为
“作品”时选择既有文集或填写新文集名称。新文章一律 `draft: true`，占位正文
已带好第一个段评锚点，创建后直接跳入编辑页。目标目录已存在会被拒绝，工作
台永远不会替您覆盖旧稿。

## 预览

编辑器右侧的近似预览只用于排版参考，明确标注“转换预览，不代表最终网站
效果”。真实效果以 Hugo 预览为准：文章卡片的［预览］、编辑页的
［Hugo 真实预览］、首页的［启动预览］都会启动（或复用已在运行的）
`http://127.0.0.1:1313/` 含草稿预览并打开对应页面。关闭工作台时，由它启动
的预览进程会一并停止；如果您自己用 `bash scripts/preview.sh` 起过预览，
工作台会识别并直接复用，不会重复启动。

## 搜索

首页搜索框对标题、副标题、分类、标签、人物、地点、文集名与正文做大小写不
敏感的子串匹配；正文命中的结果会显示一段上下文摘要（自动去掉锚点注释）。
输入即搜（300ms 防抖），清空搜索框回到分组列表。

## 版本管理（Git）

**Git 是唯一的历史来源**：工作台不自己保存版本历史，文章卡片上的保存备份
（`.cache/studio/backups/`）只是防误删的短期兜底。顶栏“版本”页显示：

- 仓库状态：当前分支、是否干净、未提交文件清单（路径、状态徽章、修改
  时间）——包括其他工具产生的改动，全部如实列出；
- 建议提交信息：按未提交文件自动生成的文案（例如“更新 2 篇文章：第一章、
  第二章”），可直接编辑；
- 提交：勾选要提交的文件 → 点［提交勾选文件］→ 确认条明示“将在本地
  创建 Git 提交”→ 再点确认才真正执行。**提交永远是手动确认触发的**，
  工作台不会自动提交，也不会推送、回滚或做其他任何 Git 写操作。

每篇文章卡片上有［版本］入口，进入该文章的版本历史页：提交时间线逐条
列出（hash、日期、信息），点“查看变更”展开这一次提交的 diff；顶部的
［查看当前未提交修改］显示工作区相对最近一次提交的 diff。

### Diff 里的段评锚点为什么默认折叠

diff 里 `<!-- paragraph-id:... -->` 这类锚点注释行对阅读改动没有帮助，
默认折叠为“段评锚点（已隐藏 ×N）”占位条，点击可展开查看；每个 diff
底部还有［显示完整原始 diff］开关，可查看一字未动的原始文本。diff 按
文件分块，增行绿底、删行红底（深浅色都适配），并标注“第 N 行附近”。

## 媒体库

顶栏“媒体”页按文章分组列出 `content/` 里的全部图片：缩略图、名称、
尺寸、大小，封面图（cover.*）与 `images/original/` 原始图有专门标记。

- **上传**：选择文章 + 选择文件（JPG/PNG/WEBP/GIF，≤20MB）。工作台会
  验证它确实是图片、按 EXIF 校正方向并去除 EXIF、最长边超过 2400 时
  等比缩小，然后以 `image-NN.<扩展名>`（序号自动递增，不覆盖既有文件）
  写入文章 bundle 根目录，同时把原始字节保留到 bundle 的
  `images/original/`。成功后给出 `![描述](image-NN.jpg)` 引用，复制后
  粘贴到编辑器正文即可；原图超过 5MB 会有提醒（不阻止）。
- **复制引用**：每张图片一键复制 Markdown 引用。
- **删除**：仍被该文章 `index.md` 引用的图片禁止删除（请先在正文里移除
  引用）；删除不是真删，文件会移入 `.cache/studio/trash/<时间戳>/`
  回收站，需要时可手工找回。

## 阅读反馈（段评/章评审核）

顶栏“反馈”页是读者段评/章评的审核台，数据来自本机评论服务
（`127.0.0.1:4317`，与线上同一套 comments-service，本地数据库在
`.cache/comments-local/comments.sqlite3`）。

- **启动服务**：首页“阅读反馈”卡片或反馈页的［启动评论服务］会以进程组
  运行 `scripts/comments-local.sh`（先完整构建网站再起服务，首次启动可能
  要一两分钟，界面会提示耐心等待，请别重复点）。如果您自己已经在跑评论
  服务（4317 端口被占用），工作台会直接复用，不会重复启动。关闭工作台时，
  由它启动的评论服务会一并停止。
- **首次建立站主账号**（只需一次，在终端执行）：

  ```bash
  printf '你的长密码' | COMMENTS_DB=.cache/comments-local/comments.sqlite3 \
    node --experimental-sqlite comments-service/src/cli.js create-admin owner
  ```

- **登录**：反馈页输入站主用户名/密码。登录会话（cookie 与 CSRF 令牌）
  只保存在工作台内存里，不落盘；关闭工作台或点［退出登录］即失效，
  会话过期后界面会要求重新登录。
- **审核**：筛选条可按状态（待审核/已通过/已拒绝/垃圾/已隐藏/已删除/
  孤立）、类型（段评/章评）、文章与关键词过滤；统计卡显示待审核/已通过/
  垃圾/孤立数量。每条评论卡片显示昵称、时间、文章标题与正文；段评会同时
  显示“提交时摘录”和“当前摘录”——正文改过后两者会不一致（卡片会明确
  提示），段落删除后会提示评论已无法定位。操作有［通过］［拒绝］［垃圾］
  ［隐藏］［删除］：删除需二次确认，且评论服务端是**软删除**（记录仍在
  数据库，只是默认不再显示）。［查看原文位置］会启动 Hugo 预览并打开
  对应文章的对应段落（章评则定位到章评区）。
- **下一条待审核**：点反馈页工具栏的［下一条待审核］进入快捷处理模式，
  待审核队列（先段评后章评）逐条以大卡片展示，［通过并下一条］
  ［拒绝并下一条］［跳过］，处理完显示完成态。
- **章评说明**：章评（对整篇文章的评论）由站点 V0.4.0 的评论系统提供，
  前台在文章页底部、段评按段落挂在段尾；作者台只做统一的审核入口，
  不改变评论服务的任何行为。

## 作者批注

作者评是您写给自己的批注，与读者评论完全无关：它按文章稳定 articleId 存放在
`data/author-notes/<articleId>.yaml`，和 index.md 一样受 Git 与保存备份保护，
但不属于 Hugo Page Bundle，因此裸 Hugo 也不会把源文件复制到公开目录。
编辑页右侧预览会在每个可批注的正文段落旁显示［写作者评］。点击后即可在
原段落下方输入，并选择［保存草稿］或［保存并发布］；已经有作者评的段落会
显示数量，也可以继续添加。Front Matter 面板下方的“作者评”面板继续作为
集中管理入口：列出本篇全部段落评和篇章评、草稿/已发布状态及更新时间，
并提供编辑、重新关联、删除和新增篇章评功能。原来的［新增段落评］下拉入口
仍保留，供需要精确选择锚点时使用。

文件结构：

```yaml
version: 1
notes:
  - id: note-a1b2c3d4e5f6   # 自动生成
    scope: paragraph        # paragraph=挂在某段；article=整篇
    paragraphId: p-30caf8624001   # scope=paragraph 时必填，且必须存在于该文当前锚点
    body: 批注正文（1–5000 字）
    status: draft           # draft=仅自己可见；published=发布到前台
    created: 2026-07-31
    updated: 2026-07-31
```

- **草稿/发布**：只有 `status: published` 的批注会出现在网站页面上，
  草稿只留在 data 源文件里给您自己看。Hugo 从 data 读取并在构建阶段过滤，
  不再依赖构建后的删除补救；裸 Hugo 与正式构建测试都会扫描全部产物，确保
  **草稿和源 YAML 均为零命中**。published 内容作为安全转义的语义 HTML 输出，
  指纹化同源脚本只把现有段评节点移动到对应段落，不使用内联脚本或 innerHTML。
  前台展示形态：段落评在
  对应段落后插入“作者评”折叠块，篇章评在正文后、章评区前汇成“作者
  章评”区块，均默认收起、衬线配朱砂边条，深浅色自适应。
- **与正文/段评的关系**：段落评靠段评锚点（`p-xxxxxxxxxxxx`）定位，
  因此新增段落评时下拉只会列出正文里真实存在的锚点；正文改动导致锚点
  消失时，该条批注在前台不再显示（文件仍保留，改回锚点或改挂其他段落
  即可恢复）。**锚点失效不会静默放过**：已发布段落评的锚点不存在时，
  首页“阅读反馈”卡片会显示“失效批注 N”，且发布前检查（preflight）
  会直接失败并列出失效清单——在编辑页「作者评」面板把它改为草稿、
  重新关联段落或删除后，检查才能通过、才能发布。保存批注**永远不会
  改动 index.md**。
- **写入安全**：与文章保存相同的事务（先备份到
  `.cache/studio/backups/<栏目>-<slug>/notes-<时间戳>.yaml`，保留 10 份，
  再原子替换），删除批注前也会先备份。
- 首页“阅读反馈”卡片会显示全站作者评草稿总数。

## 发布中心

顶栏“发布”页把发布流程收拢成三步，底层仍是既有的 `scripts/build.sh`、
`scripts/check.sh` 与 `scripts/publish.sh`，没有改动它们：

1. **看状态**：本地版本（VERSION）、CHANGELOG 最近发布记录、最近提交，
   以及服务器配置状态——只显示“已配置/未配置”，**密钥值永远不会显示
   在界面上**。
2. **发布前检查**：点［运行发布前检查］跑 `scripts/build.sh`（勾选
   “完整检查”则跑 `scripts/check.sh`，数分钟），日志原样显示。检查
   通过后的 30 分钟内才允许发布，超时需重跑。
3. **确认发布**：点［确认发布］→ 确认条明示“将上传并切换线上版本”
   → 再点确定才真正执行 `scripts/publish.sh`，全程日志显示在页面上；
   任何一步失败都停在该步并展示原因，服务器侧由脚本自身的原子切换
   保证不留半成品。

### 如何配置 .author-settings

发布需要服务器地址与域名。在项目根目录新建 `.author-settings` 文件
（已在 .gitignore 中，不会进入 Git 或发布包），每行一条：

```text
WRITING_SSH_TARGET=root@你的服务器IP
WRITING_DOMAIN=你的域名
```

发布中心只会读取 `WRITING_` 前缀的键并传给发布脚本；缺少必需键时发布
不会启动并提示缺哪一个。

## 第一次使用（Mac）

如果项目里已经有 `.venv-importer` 目录（双击过 `import-docx.command` 导入过
Word 就有），则**无需任何安装**，直接跳到下一节。

如果没有，先双击项目根目录的 `import-docx.command` 完成一次环境初始化（它会在
项目内建立 `.venv-importer` 并安装固定版本依赖；这个目录不会进入 Git、备份或
发布包）。

## 如何启动与关闭

三种启动方式任选其一：

1. 双击项目根目录的 `studio.command`；
2. 在终端进入项目目录，运行 `npm run studio`；
3. 在终端运行 `bash scripts/start-studio.sh`（可加 `--port 端口号` 换端口、
   `--no-browser` 不自动打开浏览器）。

启动成功会显示：

```text
《历代纪》作者工作台已启动 http://127.0.0.1:4173
```

并自动打开浏览器。关闭：在启动它的终端窗口按 `Control+C`（双击启动的，直接
关闭那个黑色终端窗口即可）。关闭时会自动清理临时文件和它启动的预览进程。

## 如何导入 Word

点击顶栏的“Word 导入”进入六步向导：

1. 第 1 步：点击虚线框选择，或把 `.docx` 拖进去。只接受 `.docx`、不超过
   100MB；文件名建议沿用 `《文集名·文章名》.docx`，系统会据此推断标题、
   slug 与文集。
2. 第 2 步：等待解析进度逐条打勾。失败会显示明确原因（例如文件不是有效的
   docx），不会有半成品写入网站。
3. 第 3 步：阅读导入报告（见下文“如何处理导入警告”）。
4. 第 4 步：核对元数据。**保持“导入为草稿”勾选**；slug 只能用英文小写、
   数字和连字符。如果提示冲突，请修改 slug 或换文集（见下文“如何处理路径
   冲突”），有冲突时无法进入下一步。
5. 第 5 步：检查预览。“近似渲染”只是排版参考，最终效果以 Hugo 预览为准；
   可以点击“打开 Hugo 真实预览”在 `http://127.0.0.1:1313/` 查看真实页面
   （含草稿）。点击警告可以高亮对应的近似段落。
6. 第 6 步：确认将要新建的文件清单，点击“导入为本地草稿”。成功后可以
   直接“打开草稿目录”。

## 导入的文件保存在哪里

- 正式成果：文章目录建在 `content/` 下（作品在 `content/works/<文集>/<slug>/`，
  随笔在 `content/essays/<slug>/`，资料在 `content/archives/<slug>/`），包含
  `index.md` 与 `images/` 图片目录，默认 `draft: true`（草稿）。
- 临时文件：上传的 Word 原件与解析中间态放在项目 `.cache/studio/` 下的
  一次性会话目录里，关闭工作台时自动删除；`.cache/` 不会进入 Git 或发布包。
  唯一的例外是 `.cache/studio/backups/`——那里是每次保存前的文章备份
  （见上文“备份在哪里、如何恢复”），会一直保留。

## 如何查看本地预览

工作台第 5 步和导入成功页都有“打开 Hugo 真实预览”按钮，会在
`http://127.0.0.1:1313/` 启动含草稿的完整网站预览。也可以不用工作台，直接
运行 `bash scripts/preview.sh`。关闭工作台时，由它启动的预览会一并停止；
如果 1313 端口被其他程序占用，预览会启动失败，请先退出占用者。

## 如何处理导入警告

警告**不会阻止导入**，逐条看即可：

- `未识别样式`：某个 Word 样式工具不认识，已按普通段落转换；第 5 步点击该
  警告可高亮对应段落，检查排版是否符合预期；
- `脚注暂不支持`：脚注内容导入后会丢失，请把必要注释放回正文或导入后手工补；
- `表格已转换`：合并单元格等复杂格式可能变形，在预览里核对；
- `链接图片未下载`：Word 里引用了外部图片，工作台不会联网下载，请改为嵌入；
- `空段落已忽略`、`文本框`：一般无碍，文本框内容请人工核对位置。

## 如何处理路径冲突

冲突**会阻止导入**，常见两种：

- `目标已存在`：`content/` 里已有相同目录（通常是同 slug 的旧稿）。换一个
  slug，或先确认旧稿可以删除后手工移走旧目录再导入；
- `slug 已被使用` / `articleId 已被使用`：slug 或 articleId 与别的文章重复，
  修改 slug，或把 articleId 留空让系统自动生成。

工作台永远不会替您覆盖旧稿。

## 导入失败了怎么办

- 解析失败：什么都不会写入，修复文件后重新上传即可；
- 写入中途失败（极少见，如磁盘满）：工具采用“先写临时目录、校验后再整体
  替换”的方式，失败时自动清理，不会在 `content/` 留下半个文章目录；
- 工作台异常退出（断电等）：`.cache/studio/` 可能残留本次会话的临时目录，
  下次启动时会自动清扫，也可直接删除 `.cache/studio/`（注意 backups/
  子目录是保存备份，删掉就没有可恢复的历史版本了）；
- 导入成功后想撤销：直接删除 `content/` 下刚生成的那个文章目录即可（草稿
  尚未发布，删除即完全撤销）。

## 为什么 Markdown 仍是权威稿件

网站由 Hugo 从 `content/` 里的 Markdown 构建，**Markdown 才是最终发表的内容**；
Word 只是输入方式。导入一旦完成，之后的一切修订都应在 Markdown（或重新导入
新 Word）上进行。近似渲染页面也明确标注了“转换预览，不代表最终网站效果”。

## 为什么 Word 不与 Markdown 双向同步

双向同步需要猜测“同一段文字两边各改了什么”，任何猜错都会静默丢稿。本项目
选择单向、可检查的流程：Word → 导入报告 → 人工确认 → Markdown 草稿。每次导入
都生成明确的文件清单与警告，作者始终知道将要发生什么；宁可多一步确认，也不
让工具替作者改稿。

## 如何运行测试

```bash
bash scripts/check-studio.sh   # 只跑工作台测试
bash scripts/check.sh          # 跑全部检查（含工作台）
```

测试使用临时目录搭建最小项目骨架，不会触碰真实的 `content/`。
